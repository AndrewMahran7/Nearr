# V2 account-transfer design from the proven ownership model — historical plan

**2026-10-09 successor:** The implementation described as pending below has now been superseded by the five local-only migrations `20261009000001` through `20261009000005`, with final evidence in `OWNERSHIP_INVARIANT_DESIGN.md` and `V2_TRANSFER_FINAL_QUALIFICATION.md`. In particular, the unique-save owner move uses a composite-FK cascade, not a later separate child UPDATE; child-only/deferred checks were insufficient under concurrency. This document remains the original product-semantic design, not a current deployment status or authorization.

The forensic result resolves the core question: `saved_place_sources.user_id` must equal its parent saved-place owner. It is **not** a historical creator field. Global source identity/media may be shared; each saved-place↔source association is user-owned. The old v1 unique-save transfer is the high-confidence cause of the observed mismatch: it changes only the parent owner, and the grant/timestamps match that path. A historical SQL execution log was not available. Development's `20260928000001_onboarding_real_saved_place_transfer.sql` repeats that omission and its duplicate branch deletes the source save, cascading source links. Do not promote either behavior.

## Authorization and transaction envelope

`begin_*_v2` must require the authenticated anonymous source to own the onboarding session, issue a high-entropy expiring one-time grant, and not require a server tutorial saved-place row (the build-58 tutorial fixture is local-only). `complete_*_v2` must require a permanent destination authenticated as `auth.uid()`, lock the grant and session, bind the destination once, reject expiry/tampering/foreign IDs, and replay a completed result only to the same destination. Existing established-account sign-in takes the normal sign-in path, not anonymous transfer.

One PostgreSQL transaction locks grant/session, then source/destination saves in deterministic `(user_id,place_id,id)` order, then source links and affected dependent rows. Retry or concurrent callbacks serialize on the grant. If a lock, precondition, merge, or final assertion fails, **ROLL BACK all changes**. The response is stored in the grant in the same commit; lost HTTP responses return that result on replay.

## Exact saved-place/source outcomes

| Case | Required final graph |
|---|---|
| Zero real saves / local tutorial fixture only | Complete account conversion with zero database save moves. Do not parse a synthetic tutorial ID as a UUID or create/delete a real save. |
| Unique real save | Preserve source `saved_places.id`; change its `user_id` to destination, then change **every** associated `saved_place_sources.user_id` to destination within the same transaction. Preserve source-link IDs, identities, URLs, notes, reminders, visited state, and primary flags. Reconcile any owner-scoped notification/job/result/task/run references under an explicit tested allowlist; reject active in-flight work rather than racing it. Assert zero mismatches before commit. |
| Duplicate place (`USER_A` and `USER_B` both saved same `place_id`) | Keep `USER_B`'s saved-place ID and all of its metadata/links. Keep `USER_A`'s save and links intact during conversion; **do not delete it**. For each A source identity missing under B, INSERT a new B-owned relationship with copied allowed provenance/metadata and nonconflicting primary status, `ON CONFLICT(saved_place_id,identity_key) DO NOTHING`; for an identity already under B, preserve B's row/ID and do not create a duplicate. Do not mutate other users' links or global `place_video_media`. Do not clean up A's account until all relevant history/metadata is reconciled in a separate reviewed step. |
| Multiple source links / source used by multiple places or users | Apply the above independently per saved place and identity. A canonical content identity may legitimately have many user-owned links; never globally dedupe or delete it. |
| Metadata conflict | Never overwrite B's nonempty notes, AI note, visited/reminder preference or category override. Copy A's value only into an empty B slot under an explicit field rule. If both hold different nonempty user-authored content, or A has dependent notification/queue/public-share state without a reviewed transfer rule, abort with a typed conflict and retain both graphs. Do not silently discard A's data or let anonymous-account cleanup erase it. |

The duplicate strategy is intentionally **copy association, retain original**, not move or delete. `scripts/testSourceOwnershipTransferFixtures.sql` exercised that shape against the isolated Production schema: A's two links remained, B kept its existing primary and gained one missing identity, an existing same-identity insert was a no-op, and all fixture rows rolled back. Unique-save parent+child owner movement also passed locally. These are domain fixtures, **not** a complete V2 RPC or concurrency proof.

## Additional preconditions and prevention

- Refuse a transfer involving any pre-existing parent/child owner mismatch until a separately reviewed repair resolves it. `SOURCE_Y` must not be silently swept into a V2 conversion.
- Treat share jobs, media tasks, result rows, notification events, public shares, recognition rejection references, and account cleanup as explicit graph edges. Active jobs/tasks block transfer; terminal-history ownership/remapping must be implemented and tested before source-account cleanup is allowed. No broad `WHERE user_id=USER_A` migration of unrelated jobs.
- Final transaction assertions: no duplicate `(destination,place)` save, no duplicate destination `(save,identity)` link, every transferred/created child owned by its parent owner, no missing source identity in the destination, no changed third-party relationship, and all affected owner-scoped references coherent.
- Maintain v1 RPCs for public 1.4.55. V2 uses new names only; do not replace old signatures. After repair and writer inventory, a deferred database-level owner invariant plus a read-only integrity gate should prevent a parent-only owner update from recreating this bug.

**Open before a Production migration:** implement the RPC; define/test the exact dependent-row and metadata-conflict rules, account cleanup, adversarial RLS, two-session concurrency, lost-response replay, and cross-version contracts. No Production migration or deployment is authorized by this design document.
