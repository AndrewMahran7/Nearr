# Source ownership domain model

Decision: **YES — a `saved_place_sources` relationship owner must equal its `saved_places` owner.** This is supported by the live owner-enforcement trigger, authenticated SELECT policy, source-attachment RPC, migration backfill, and both client hydration paths. Cross-user reuse of the *same content identity* is legitimate; cross-owner ownership of one *relationship row* is not.

- Global/reusable: `places` (canonical place), `identity_key` (canonical content identity), and `place_video_media` (place/content media with explicit visibility rules). None gives a caller another user's saved-place membership.
- User-owned: `saved_places`, its notes/reminder/visited/legacy-source fields, and each `saved_place_sources` association. The association's `user_id` is a denormalized authorization owner, not the original sharer. The original URL, attachment timestamp, transfer grant/session, and share-job evidence carry provenance.
- Contextual: `recognition_source_states.owner_user_id` depends on visibility scope; it is not the association owner. Public-share `created_by` is the share creator; its `source_id` may point to a relationship but does not transfer its ownership.

For a unique-save account transfer, keep the saved-place ID and move the parent and every child association owner together within one transaction, with dependent owner-scoped rows handled explicitly and a zero-mismatch postcondition. For a duplicate-place transfer, keep the destination save ID. Materialize every source identity missing there as a destination-owned association (preserving source metadata and identity); leave an already-present destination association intact and fill only explicitly approved missing metadata. Preserve the anonymous source save/link until separate authorized cleanup; do not delete it merely to satisfy uniqueness. A source identity may appear under several users without giving any user the others' relationship rows.

Prevention should first make privileged transfer/correction code use a single reviewed owner-change path with locks, assertions and failure rollback, and run a read-only owner-mismatch release check. After the historical row is repaired and all writers inventoried, consider a **deferred constraint trigger** covering parent owner changes and child changes so the equality is checked at transaction end. Do not install a blind immediate parent trigger: the unique-save transfer temporarily changes the parent before its children within one transaction. No schema change is proposed or applied in this forensic task.
