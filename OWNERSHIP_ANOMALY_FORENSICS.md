# Ownership anomaly forensics — REPAIR REQUIRED, not yet repaired

Production was queried read-only. `USER_A` (anonymous) originally owned `PLACE_X` and its one `SOURCE_Y` Instagram association. A completed grant bound that anonymous session to established `USER_B`. The old v1 transfer moved `PLACE_X.user_id` to `USER_B` but left `SOURCE_Y.user_id=USER_A`. The relation's URL/platform match the saved place's legacy primary-source mirror; both owners still exist. No identifying values were printed or committed. Exact IDs are in the encrypted local map described in `OWNERSHIP_ANOMALY_TIMELINE.md`.

## Why this is not intentional provenance

1. The source-link INSERT/UPDATE trigger requires `saved_place_sources.user_id=saved_places.user_id`; RLS grants authenticated users SELECT only when the link's `user_id=auth.uid()`. The schema describes ownership, not creator attribution.
2. The creation backfill and `attach_saved_place_source` use the saved-place owner as the child owner. The client reads child links under owner-scoped saved places. No `original_user_id` or `created_by` column exists on this relation.
3. The transfer grant/session preserve the historical anonymous identity separately. A global source/content identity is represented by `identity_key` and `place_video_media`, not by leaving the relationship assigned to a prior user.
4. The v1 transfer's unique-save branch changes the parent owner but contains **no** child-source reference. Timestamps and grant result fit that branch exactly. The Development V2 migration repeats the omission and additionally deletes duplicate source saves before their child relations are reconciled; it must not be promoted.

## Current graph and client/security effect

- `PLACE_X` belongs to `USER_B`; `SOURCE_Y` still belongs to `USER_A` by RLS. `PLACE_X` has one source child, and `USER_A` has no save of that canonical place. `USER_B` has one.
- Isolated restored-schema RLS test: `USER_A` sees 1 source child / 0 parent saves; `USER_B` sees 0 child sources / 1 parent save. Neither authenticated role has UPDATE or DELETE grant on `saved_place_sources`. Thus the UI cannot fix it. The stale child exposes its content metadata and `USER_B`'s saved-place UUID to the former anonymous identity; it does **not** grant access to `USER_B`'s parent row or notes. The grant ties the two identities through a conversion flow, but that does not justify the stale RLS relationship.
- Public 1.4.55 and build 58 both miss this child in direct source hydration. Both can still show the single Watch/source link using the parent legacy mirror; the mirror URL/platform match the child, and the parent has an AI note. No creator/caption/thumbnail data is present on this child, so a visible regression for this account is not proven. The source-group fallback works while this save has no other visible child; adding a new visible child could suppress that fallback and make `SOURCE_Y` disappear from source grouping. `placeSourceCards` retains its own legacy fallback. The gallery Edge function derives ownership from `USER_B`'s saved-place ID and can query the child with service role, but this particular source has no thumbnail/frame, so a gallery tile is not guaranteed.
- `PLACE_X` has one `nearby` event owned by `USER_B`, one notification count and one reminder opportunity; no notes, visit, or archive flag. No job/result/media-task/rejection/public-share reference points to this particular save/source at the audit snapshot. Four other user-owned links have the same canonical content identity; a global `place_video_media` row exists. Do not delete that global source or the other users' links.

**Classification: REPAIR REQUIRED.** The row violates a schema/RLS ownership invariant and creates an orphaned association from the client's perspective. Immediate data loss or access to another user's notes was not observed, but future source grouping and security behavior are wrong. The proposed repair is a single child `user_id` correction after strict re-verification, not a saved-place/source deletion. It was tested locally and **not executed in Production**.
