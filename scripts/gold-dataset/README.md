# Gold recognition benchmark tooling

The core dataset commands are local and do not call recognition providers, deploy code, or change the app. Separately authorized live experiments use the paid coordinator described below. Source manifests, private labels, split assignments, materialized inference input, and observations are separate files. See the [manifest schema](../../artifacts/recognition-gold-dataset/schema/dataset_manifest.schema.json), [label schema](../../artifacts/recognition-gold-dataset/schema/dataset_labels.schema.json), and [observation schema](../../artifacts/recognition-gold-dataset/schema/observation.schema.json).

`dataset_manifest.jsonl` contains **one real post per line** and no ground-truth label. Case and group IDs are opaque. For platform IDs use the actual Instagram/TikTok/YouTube/Facebook content ID. If the ID cannot be recovered, retain the complete public URL; the validator hashes the *whole* URL, including `?v=`. Confirmed reposts and mirrors share a source group. Cross-platform mirrors require manual confirmation. Historical posts may have `retrieval_date: null`, with `inventoried_at` and `source_record_date` recorded separately.

`dataset_labels_private.jsonl` contains accepted truth, aliases, place groups, provenance, depicted versus mentioned-only roles, approximate segments, and review decisions. An unresolved case may use `proposed_places` for private research hypotheses; it must keep `expected_places` empty. Every depicted exact place on a ready case needs its own `place_group_id`, also listed in the label's `place_group_ids`. The file is ignored by Git. So are the held-out manifest, seal, review pages, mapping files, and per-case scores. Keep a backed-up, access-controlled copy of private files outside this repository; Git history cannot recover them. An encrypted team store with a versioned digest is appropriate. When moving worktrees, export the private files explicitly through that store and check SHA-256 after import. Never paste held-out labels into an issue, PR, public branch, or model prompt.

The public committed manifest should contain development/calibration cases only. For a future holdout, keep its source records in `heldout_manifest_private.jsonl`, then create a **local combined manifest** under `.local/recognition-gold-dataset/` for validation, sealing, materialization, and scoring using `--manifest`. A public manifest with answer-bearing captions and source links is not sealed merely because the accepted label is in another file.

Commands (all use local files and make no network request):

```powershell
npm run dataset:validate
npm run dataset:split
npm run dataset:materialize -- --case g_0123456789abcdef --view visual_only
npm run dataset:review -- --case g_0123456789abcdef
npm run dataset:score -- --split development --view full --observations .local/recognition-gold-dataset/observations.jsonl
npm run dataset:seal
```

All commands accept `--manifest`, `--labels`, and `--splits`. Materialization also validates split assignment. `dataset:split` is a deterministic **proposal** based on connected source and place groups; freeze and review it before use. Any historical outcome forces its component to development. New cases without independent manual review also stay in development. `dataset:seal` requires the combined manifest under the ignored `.local/recognition-gold-dataset/` tree. It refuses fewer than 200 benchmark-ready posts or fewer than 60 held-out cases/source groups, verifies local frame hashes, and checks every held-out label's independent review and provenance. Each visual candidate needs a `mask_review` with `answer_fields_checked:true`, `permitted_media_derivative:true`, reviewer and timestamp, plus `evidence.frame_sha256` matching its actual files. The seal also requires single/multi/negative labels, all masked-view slices, misleading metadata, at least two platforms, five categories, and three countries in the holdout. These are minimum presence checks, not a claim of balanced sampling. An empty holdout is the correct state until those checks pass. Held-out scoring or materialization requires `--explicit-heldout --milestone baseline_v1` or `--milestone final_candidate_v1` plus a matching local seal that predeclares that milestone. Freeze the final candidate configuration before held-out inference; never use individual held-out failures for same-generation tuning. A private milestone ledger prevents an unnoticed repeat under a new output filename. It writes aggregates to the chosen output and per-case rows only under the ignored `.local` directory.

Materialization supports six standard views: `full`, `description_hidden`, `location_hidden`, `visual_audio`, `visual_only`, and `text_only`, plus optional separately reviewed `visual_pixel_text_masked`. These are views of **retained evidence**. Video/audio must first be represented by explicitly captured transcript and/or frames; the tool does not fetch a social video or silently turn a source URL into model input. `visual_only` requires actual frame paths and preserves legitimate text embedded in video pixels. Strong scene-only exact cases are counted separately. The materializer decodes and re-encodes images with FFmpeg, strips metadata, and uses neutral numbered filenames. It writes `input.json` with an opaque input ID, allowlisted evidence fields, source-derived video duration and aligned frame timestamps, and a disabled candidate cache. Timing preserves full-video frame selection without exposing identities or labels. Case-ID mapping lives outside the input directory. Source paths/URLs, IDs, answer annotations, labels, groups and split assignments stay out of inference input. The recognition adapter must receive only `input.json` and neutral frames; it must not read source manifests, mappings, private labels or answer caches.

These checks address accidental leakage in our trusted local tools. They are not a security sandbox against arbitrary code with filesystem access. Run inference in a separate process/workspace with access limited to materialized input if a sealed evaluation is conducted.

Current visual collection uses the ignored .local/recognition-gold-dataset/benchmark_manifest_private.jsonl, benchmark_labels_private.jsonl and benchmark_splits_private.json; pass all three explicit paths to the CLI. The committed original 124-row manifest is preserved source history, not the current runnable snapshot. See artifacts/recognition-gold-dataset/DATASET_COMPLETION_GATE.md for current counts and baseline restrictions.

Scoring includes READY cases only. Primary correct autonomous resolution and autonomous coverage use every exact case, including difficult cases previously marked unreasonable for autonomy. Precision counts all autonomous place outputs on adjudicable cases. Review/failure rates, candidate recall at 1/3/5/N, branch proof failures, and descriptive 95% Wilson intervals accompany these rates. Variant comparisons must additionally account for connected source/place groups. An exact multi-place set is autonomous success only when multiple places were detected. Brand plus city cannot prove a coordinate-anchored branch without a matching place ID, coordinates or accepted address.

## Paid inference and immutable replay

`paidBatch.mjs` validates a frozen runtime and neutral input list, records expected calls/providers/cost and retry-inclusive caps, and launches a separate inference process with provider credentials only. Every physical request reserves its maximum exposure before dispatch. Completed usage and unknown reservations both count against the $50 cumulative cap. It never loads gold labels. Freeze all four run files with `freezeInferenceRun` before scoring.

`replayEmptyEvidence.ts` applies the valid-empty review policy to an unchanged recorded normal-pass prefix. It removes the unexecuted suffix from counterfactual provider cost and candidates, while retaining full baseline latency plus local policy overhead. `replayTenantGuard.ts` tests finalizer vetoes against frozen provider outputs after proving default finalizer parity. These are label-free replays, not new paid runs or fresh latency measurements.

Unknown charges normally stop paid work. A narrowly validated `fixedRequestCarry` receipt can reconcile budget exposure for a completed batch's lost-response Google request: exact request hash, immutable ledger hash, fixed rate-card hash, and the entire reservation must match. The reservation remains committed and the charge remains unknown. Token-priced calls and unfinished batches cannot use this path. This does not turn an unknown charge into a measured charge or permit overspending.

`resumeFrozen.mjs` resumes only cases stopped before any provider dispatch, with identical recognition settings, runtime and input bytes. The originally attempted failure stays failed. Its costs remain unknown. The assembler includes original local check time, all request histories and both receipts, then freezes a complete pair before any heldout score is opened. It cannot replace an attempted bad outcome or change a model under a continuation. Any exact cost metric remains null where billing is unknown; report known-plus-reserved bounds separately and disclose any conservative sensitivity analysis.
