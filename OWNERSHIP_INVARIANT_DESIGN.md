# Saved-place/source ownership invariant

The source relationship's `user_id` is authorization ownership, not original-creator provenance. Both columns on a source relationship are `NOT NULL`. The final migration adds a unique key on `saved_places(id,user_id)` and a composite foreign key from `saved_place_sources(saved_place_id,user_id)` to that key with `ON UPDATE CASCADE ON DELETE CASCADE`. It retains the existing `saved_place_sources.saved_place_id` and `user_id` FKs, early child-owner trigger, RLS policies, and client/RPC signatures.

This is a database-level commit invariant. A parent owner change is now a referenced-key update. A committed child with the old owner is either included in the cascade or rejected as a stale composite reference; a child inserted after the parent moves cannot reference the absent old `(save ID,owner)` pair. Child-only checks and caller lock conventions do not offer this guarantee because a BEFORE INSERT check can observe the old owner before the insert's FK work waits. The prior rejected V2 candidate demonstrated exactly that split. PostgreSQL documents both composite foreign keys and `ON UPDATE CASCADE` as copying referenced-key changes into referencing rows, and documents the conflicting key-share/update row locks: [constraints](https://www.postgresql.org/docs/current/ddl-constraints.html), [explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html).

The V2 unique-save branch updates the parent owner and relies on the FK cascade for **all** children; it does not issue a later separate child-owner UPDATE. The legacy V1 unique branch is protected by the same cascade without an interface change. V2 duplicate-place handling preserves A's save/source graph and adds only missing identities to B's existing save. The V1 compatibility amendment does the same for its one tutorial save, and fills B's empty legacy `source_url` without overwriting B-authored values. The cleanup candidate RPC excludes a converted anonymous account while it still owns a saved place/source/job/task/notification.

The FK alone guarantees ownership equality but not the product requirement that B receive a *late* new A source on a duplicate save: A's retained parent remains valid. Migration `20261009000004` therefore makes the existing child owner guard lock its parent row before a source association is inserted or its owner/save/identity changes. V1/V2 also lock the parent when copying sources. If a source commits first, transfer copies it; if transfer completes first, the guard observes the converted session and rejects the stale A association. Migration `20261009000005` closes the analogous gap for a newly created A save by locking the anonymous onboarding session before save INSERT. Transfer locks that session first; a save committed first is included in the V2 scan, and one attempted after conversion is rejected. These guards preserve history and do not rewrite an existing A duplicate graph.

The added unique index is on the immutable save ID plus its current owner; it does **not** globally deduplicate canonical source identities or prevent four other users from saving the same content. The source table's existing `(saved_place_id,identity_key)` uniqueness remains the per-save dedupe boundary. A parent deletion still cascades its children. An owner transfer updates child `updated_at` through the existing trigger, but keeps each relationship ID, save ID, source identity, and other provenance fields.

Migration `20261009000001` asserts zero pre-existing mismatches before adding and validating the constraints. A fresh post-repair Production restore began at zero and accepted the ordered migration sequence without changing restored save/source/user row hashes. Production deployment is expressly out of scope for this task; DDL acquisition/lock duration must be reviewed with the broader release rollout. No ordinary user, service-role function, or stale client can bypass a validated FK; an administrator deliberately disabling/dropping database constraints is outside the supported-writer model.
