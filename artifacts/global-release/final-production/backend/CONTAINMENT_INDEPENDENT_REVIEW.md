## Decision

Do not execute the proposed cutover under an unconditional zero-dispatch claim.** The candidate has strong, passing local server-containment and historical-client compatibility evidence. That does not establish every installed client's behavior when a backend response is unavailable. The original IPA is unavailable to the user, and the existing EAS artifact downloads below do not provide a substitute.

This is not a finding that the released client actually contains a working Gemini credential. Its tracked source contains a conditional direct route, and the standard pinned Expo pipeline strongly suggests the non-public key is not embedded. The distinction is important: conditional source evidence is not an inspection of the signed or cached runtime.

## Legacy fallback and static environment boundary

In both historical source revisions, `lib/shareExtractionBackend.ts` returns null after a non-200 response. The original `app/share.tsx` decision block then reaches the legacy fallback. `lib/aiExtractPlace.ts:395` reads bare `process.env.GEMINI_API_KEY`; if absent it returns a heuristic result without HTTP, but if present it directly calls Gemini's `generativelanguage.googleapis.com` endpoint. This route is not controlled by the worker or Supabase Edge gate. Network failure or missing backend configuration can also reach it.

The paused process-share-link candidate instead supplies the existing HTTP200/extracted transport envelope with `manual_fallback`, empty candidates/query and `searchAllowed=false`. It is **not** a successful recognition. Actual old parser plus original host decision-block tests exit before autosave or legacy AI on this response. Old code ignores the response's human message and uses its hardcoded manual-help text; async503 yields generic failure. Explicit pause copy on an old binary is therefore not verified or promised. Parsing public metadata can occur before the server response, so the pause is not a promise of zero social-site/Maps metadata traffic.

`legacy-client-environment-tests.json`: **5/5 offline checks pass** against the exact tracked public-build lock and source. Installed versions match Babel preset Expo11.0.15, Expo Metro0.18.11, Metro0.80.12, React Native0.74.5 and Expo51.0.39. The actual production-iOS transform with a harmless private sentinel does not inline bare GEMINI_API_KEY; it does inline a public EXPO_PUBLIC sentinel. The actual Metro production prelude initializes an empty environment plus NODE_ENV, yielding undefined for Gemini. The Expo development prelude also only injects EXPO_PUBLIC variables. Tracked runtime/config/plugin/patch inspection found no Gemini assignment, environment replacement or custom inline transformer; native share glue does not supply one. The only patch is an Expo dev-menu Swift simulator compatibility fix. EAS configuration has no matching key-to-public mapping. Server-oriented `lib/shareAgent/agent.ts` also defines a Gemini call, but no mobile caller to `runShareAgent` or runtime key injection was found in the inspected source.

This is strong conditional evidence for the **tracked standard build**, not proof that the inaccessible signed Build55, every cached update or native runtime exactly matches those assumptions. No credential validity probe was made.

## Required boundaries and safe options

The current safe action is to retain the tested, frozen candidate **without Production changes**, with the global proof gap explicit. Root can seek a separately scoped decision about server-side risk reduction with residual installed-client uncertainty, but that is not equivalent to passing the original global gate and is not assumed here. Credential invalidation/rotation and a new mobile/OTA rollout are separate consequential operations requiring their own reviewed scope; neither is proposed as an automatic workaround.

If execution is independently authorized later, the existing proposal's safeguards remain mandatory: re-read live drift and make a fresh non-overwriting private backup; retain existing JWT settings and auxiliary endpoints; pin exact candidate source/config rather than leave main auto-redeployment able to restore the old worker; close all ingress and queues, retire every old runtime, then verify health200/readiness503 and source hashes. Cross-service cutover is not atomic and already-dispatched requests cannot be recalled. Pending unsafe source changes or an old active replica invalidate a zero-server-dispatch claim.

Recovery must keep the database gate and paused/inert builds. Never fall back to the September provider-enabled image, remove the guard to clear errors, mark jobs successful, or overwrite current data with the historical restore. Future qualified recovery must reconcile queue leases, skipped enrichment, reservations and at-most-once notification state separately. Full1.7 release and commercial/minor provider qualification remain independent unmet gates.
